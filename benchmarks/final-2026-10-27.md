# Production TTS acceptance and concurrency — 2026-10-27

Endpoint 42781 (`ielts-qwen3-tts`), group 53004, template 781728 / `ee15fc11df5eb83d43a63b5a45d3f306`, worker `02fa3d4`. The pinned image is recorded in `deployment/production.json`. All final requests used the native Vast SDK and online vLLM-Omni 0.30.0 with precomputed profiles; direct Qwen inference was not used.

## Capacity and limits

- Endpoint: at most 8 workers; `cold_workers=0`, `min_load=0`, target queue time 10 seconds, inactivity timeout 300 seconds.
- Each worker: one Qwen3-TTS Base model, 8 concurrent talker sequences, continuous batching. Eight fully ready workers would provide 64 active talker sequences. The audio-decoder stage has its own 8-sequence scheduler.
- Controller: bootstrap 16 logical requests, then 16 per ready worker up to a default ceiling of 128; expansion requires two consecutive estimated queue-time samples above 10 seconds. No unbounded task creation.
- **512 logical jobs in flight passed** in the load test below. This is a tested operating point, not a discovered hard Vast API limit. It includes requests queued at the client, transport, worker or engine. The SDK defaults to 500 shared HTTP connections, so 512 logical jobs do not imply 512 simultaneous HTTP connections.
- The independent worker monitor observed **6 workers processing requests simultaneously**. Eight-worker steady-state throughput has not been measured.

## Final real requests

All eight voices passed on the updated deployment: alex, alex_xvec, ben, ben_xvec, jane, jane_xvec, june, june_xvec. Every result passed HTTP success, correct request/voice/mode metadata, complete nonempty mono PCM16 WAV, 24 kHz sample rate, positive duration and finite/non-silent samples. Each required one controller attempt. Acceptance text was `Ready for the science challenge?`; durations were 1.76–2.32 seconds. See `acceptance-final-2026-10-27.json`.

Unsupported voice, mismatched mode and boolean seed each returned HTTP 400. An explicitly injected HTTP 503 and then TimeoutError produced a successful real endpoint response on attempt 3, with a persisted native route request ID. The injection verifies controller behavior; it does not claim a real GPU/network outage occurred.

The startup voice check was fixed to allow vLLM-Omni's additional `default` alias while requiring all eight custom profiles. The live voices API advertised those eight plus default, with no runtime uploads. The GPU worker log confirmed precomputed profiles were used for both modes. Reference embeddings are 2048-dimensional for this checkpoint, with shared tensors between each ICL/x-vector pair.

## Sustained backlog with autoscaling

Each run used 2,048 jobs, all eight voices rotated, the same 94-character text, `seed=0`, `max_new_tokens=256`. Input: `Ready for today's science challenge? Think carefully, and explain how you reached your answer.` Each generated result passed audio and metadata validation. No output audio or credentials are stored in benchmark reports.

| Logical concurrency | Passed | Elapsed | Jobs/min | Median latency | p95 latency |
|---:|---:|---:|---:|---:|---:|
| 256 | 2048/2048 | 395.229s | 310.91 | 41.162s | 93.553s |
| 512 | 2048/2048 | 221.020s | 555.97 | 31.400s | 83.893s |

The 256 run scaled from one to three processing workers; the following 512 run reached six. **These runs are not a controlled comparison of concurrency settings**: the later run benefited from additional ready GPUs. Both include autoscaler ramp-up. Use the earlier single-RTX-5090 sweep to select per-worker concurrency: throughput plateaued around 16 in flight, at approximately 238–242 jobs/min for that earlier worker/profile-loading implementation.

Recommendation: start around 16 logical requests per ready GPU (128 for an 8-worker pool), retaining configurable headroom for cold starts and retries. Sending 512 requests to one GPU increases queue latency. Neither this workload nor the eight-worker theoretical sequence capacity establishes a universal maximum for long narration or other generation parameters.

The benchmark's optional embedded CLI monitor could not reliably run under the temporary test SDK's PYTHONPATH (`ModuleNotFoundError: vastai.cli`, exit 1). The separate monitor invoked the installed CLI in its normal environment throughout both tests; its allowlisted worker snapshots are retained in `workers-final-2026-10-27.json`. Worker processing counts use `reqs_working>0`, because Vast reports the ready state as `idle` even while requests are working. SDK-level transport rerouting is allowed in these load tests, so zero application-level failures does not imply zero internal reroutes.

## Startup, memory and limits of verification

Fresh worker 57966071 (RTX 5090) took **378.852 seconds from instance start to ready**, including image/model loading and engine warmup. Source: CLI `start_date` and the autoscaler `model_loading -> idle` transition. The acceptance request set waited 271.482 seconds for workers already starting; that is a different measurement. The earlier report's 364-second observation measured model-server startup only and has been relabeled.

During the final sustained test, worker 57964238 used **12,209–12,211 MiB GPU memory**, with sampled utilization 46–68%. These readings describe one worker, not every host. Source audio was checked against character assets; no subjective listening assessment, ASR completeness check, same-GPU direct-Qwen comparison, compiled/eager comparison or exhaustive `max_num_seqs` tuning was performed.

A fixed seed did not produce byte-identical output under continuous batching. Production determinism is achieved through canonical job identity and durable reuse of the first validated artifact. Do not promise seed-only byte determinism. Some autoscaler launches hit unavailable marketplace offers or startup deadlines; the successful application requests waited/rerouted while replicas were replaced.

## Idle verification

All six replicas that processed load stopped automatically after inactivity, preserving `cold_workers=0`. One separate worker (57966254) remained in Docker image loading for about 20 minutes and never served a request; it was explicitly removed after a stop request failed to settle, releasing the unused allocation. This is a provisioning cleanup limitation: the 300-second inactivity setting did not cancel that in-progress image pull. The final scale-to-zero JSON distinguishes automatic shutdown of ready workers from that manual cleanup. Stopped cache disks can continue to incur storage charges.
